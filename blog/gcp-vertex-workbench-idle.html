The Notebook Environment That Wasn't Needed Anymore

The data science team had been using a Vertex AI Workbench instance for exploratory model development — iterating on feature engineering, running training experiments, visualizing results. The instance was configured with an n1-highmem-8 machine type and a V100 GPU, sized for the largest datasets they needed to process interactively.

When the model reached a stable state, the team productionized training as a Vertex AI Training Pipeline with its own managed compute. The Workbench instance became redundant: the notebooks were version-controlled in Git, the experiments were tracked in Vertex AI Experiments, and the pipeline handled scheduled retraining. Nobody needed the interactive notebook environment anymore.

Nobody turned it off, either. The instance stayed ACTIVE. Twenty-three days later, a quarterly GCP billing review surfaced the line item. At $1,523/month for the V100 configuration, the team had wasted roughly $1,165 over the idle period — for a machine that hadn't been opened.

Vertex AI Workbench ACTIVE = billing. An instance in ACTIVE state bills continuously for the GCE machine type and any attached accelerators. Stopping the instance (STOPPED state) eliminates compute charges. Deletion eliminates all charges. Neither happens automatically.

Why Workbench Instances Stay Running

Vertex AI Workbench instances are easy to create and nearly invisible from a cost perspective — they appear in GCP Billing as Compute Engine charges mixed with other VM costs, making them easy to overlook. The patterns that leave them running:

  • Workflow graduation: Interactive exploration notebook environments that aren't cleaned up when work moves to production pipelines or scheduled jobs.
  • Team transition: An ML engineer who built the Workbench instance leaves or rotates to another project. The new team member doesn't know the instance exists or assumes someone else owns it.
  • Experiment preservation instinct: Teams keep instances running "just in case" they need to reproduce a result or debug something interactively. The option value is real but rarely exercised — especially for months.
  • GPU provisioning difficulty: GPU quota can be hard to obtain in some regions. Teams keep GPU instances running rather than risk being unable to reprovision one when needed.

How the Detection Rule Works

CleanCloud's gcp.vertex.workbench.idle rule detects Vertex AI Workbench instances in ACTIVE state that have had no control-plane activity for 14 or more days. It uses the updateTime field from the Vertex AI Workbench API as the idle signal.

Why updateTime rather than a user activity metric? Vertex AI Workbench does not expose a reliable "last notebook access" timestamp through Cloud Monitoring for all instance types. The updateTime field reflects the last time the instance's configuration was modified — which changes when users start/stop kernels, modify notebook content via the API, or perform any operation that touches the instance record. An instance with no updateTime movement for 14+ days is one that nobody has meaningfully interacted with.

Detection logic:

  1. State filter: Only instances in ACTIVE state are evaluated. STOPPED instances are excluded — they already don't incur compute charges.
  2. Idle window check: The rule compares the current time to updateTime. Instances with (now - updateTime) ≥ idle_days (default: 14 days) are flagged.
  3. Accelerator detection: The instance's accelerator configuration is checked. GPU-backed instances (any accelerator type and count) are treated as higher risk.
  4. idle_ratio calculation: idle_ratio = idle_days_actual / idle_threshold. An instance idle for 28 days on a 14-day threshold has an idle_ratio of 2.0.

Risk and confidence tiers:

  • CRITICAL risk: GPU-backed instance with idle_ratio ≥ 2.0 (idle for at least twice the threshold). A V100 instance idle for 28+ days on a 14-day window.
  • HIGH risk: GPU-backed instance within the normal idle window (idle_ratio < 2.0).
  • MEDIUM risk: CPU-only instance, regardless of idle duration.
  • HIGH confidence: updateTime is authoritative and clearly older than the threshold.
  • MEDIUM confidence: updateTime is missing or the instance is newer than the threshold but other signals suggest idleness.

Catching It in CI Before 23 Days Pass

With a 14-day idle threshold and weekly CI scans, an idle Workbench instance would first appear as a finding in the second week — before the team has accumulated more than two weeks of unnecessary spend.

.github/workflows/cleancloud-gcp.ymlYAML
name: CleanCloud GCP AI/ML Scan
on:
  schedule:
    - cron: '0 8 * * 1'  # Every Monday at 08:00 UTC
  workflow_dispatch:

jobs:
  cleancloud-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: GCP authentication
        uses: google-github-actions/auth@v2
        with:
          credentials_json: ${{ secrets.GCP_CREDENTIALS }}

      - name: CleanCloud — GCP AI/ML scan
        uses: cleancloud-io/scan-action@v1
        with:
          provider: gcp
          category: ai
          fail-on-confidence: HIGH

The workflow fails when a HIGH-confidence idle Workbench instance is found. For GPU instances (T4, V100, A100, L4), the finding is HIGH confidence as soon as the 14-day threshold is passed. The team gets a notification in week 2, not week 4.

Stopping the Cycle of Forgotten Notebooks

Workbench instances are one of the highest-frequency idle resource patterns in GCP AI/ML environments. The instinct to keep them running is understandable — they take minutes to provision but represent hours of environment setup. Some practices that help:

  • Stop instances at the end of every work session: Make stopping the Workbench instance part of the end-of-day routine. A stopped instance costs nothing for compute; it only incurs disk storage charges.
  • Use Vertex AI Workbench idle shutdown: The managed notebooks feature includes a configurable idle shutdown timer. Set it to 60 minutes for development instances. This won't help with instances that were intentionally left running for batch tasks, but it catches sessions left open accidentally.
  • Prefer training pipelines over interactive training: For any training run exceeding 30 minutes, run it as a Vertex AI Custom Job rather than in a notebook. Custom Jobs provision compute on demand and terminate automatically.
  • Run CleanCloud weekly on AI resources: Weekly scans with HIGH confidence alerting surface idle GPU instances within two weeks of the last activity.

Frequently Asked Questions

Does stopping a Vertex AI Workbench instance preserve my notebooks?

Yes. Stopping an instance (transitioning to STOPPED state) preserves the boot disk, data disks, and all notebook files. Compute charges stop; disk storage charges continue at standard GCS/PD rates. When you start the instance again, it resumes from where you left off. Deletion removes all data permanently.

What is the difference between Vertex AI Workbench and Vertex AI Workbench Instances (managed)?

Vertex AI offers two notebook environments: the original user-managed Notebooks (based on Compute Engine VMs) and the newer managed Workbench Instances. The gcp.vertex.workbench.idle rule covers both. The detection signal (updateTime from the Notebooks API) applies to both instance types.

Why does CleanCloud use updateTime instead of a kernel activity metric?

Vertex AI Workbench does not expose a standardized "last notebook kernel activity" metric through Cloud Monitoring across all instance types and configurations. The updateTime field from the control plane API is reliable, consistently available, and changes whenever any meaningful user or system action touches the instance record. It is a conservative signal — some instances with zero kernel activity might have had configuration changes — but it is the most dependable idle proxy available across both managed and user-managed instances.

Will CleanCloud flag my Workbench instance if I use it weekly?

No. If you access your Workbench instance at least once within the idle_days window (default: 14 days), the updateTime will be updated and the rule will not flag it. Teams with weekly usage patterns should consider setting idle_days: 21 to avoid false positives during normal work patterns with occasional gaps.
