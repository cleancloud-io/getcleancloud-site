Vertex AI Feature Store:
$197/Node/Month for a Store Nobody Is Querying

A recommendation system was decommissioned. The Vertex AI Feature Store that served its real-time features was not. Five months of Bigtable-backed online storage billed at $591/month — $2,955 for a store that received its last ReadFeatureValues request the day the product was retired.

What Is Vertex AI Feature Store?

Vertex AI Feature Store is a managed service for storing, serving, and sharing machine learning features. It solves the "training-serving skew" problem — ensuring the same feature transformations used during model training are available at inference time, with low latency.

The service has two generations:

  • Legacy Featurestore: The original Vertex AI Feature Store, using Bigtable as the backing store for online serving. Features are organized into entity types and feature groups within a Featurestore resource. The cost driver is the number of Bigtable nodes allocated to the online store.
  • New-gen Feature Store: A newer architecture with different billing mechanics. Also covered by CleanCloud's idle detection.

For Bigtable-backed online stores, billing is based on node count, not on query volume. An online store with three Bigtable nodes bills approximately $591/month whether it serves 100 million feature requests or zero.

Bigtable billing model: ~$197 per Bigtable node per month, regardless of read or write volume. An online store provisioned with 3 nodes costs ~$591/month at idle — indefinitely, until deleted.

How Feature Store Waste Happens

Feature Store waste follows the same pattern as other managed AI infrastructure: created for a specific model or use case, that use case ends, the infrastructure stays.

But Feature Stores have a specific failure mode that makes cleanup even less likely:

  • Tied to a deprecated model, not to serving infrastructure: When a model is retired, teams commonly delete the serving endpoint and training pipelines. The Feature Store is lower-profile — it's not in the critical path of the serving call, so it doesn't show up in post-mortem cleanup checklists.
  • Shared stores with partial activity: A Feature Store created for recommendation features may also contain features for a fraud detection model that's still active. The store appears "in use" — but only one entity type is active. The Bigtable node count was sized for both workloads.
  • PoC stores not deleted: Feature Stores are often created during model experimentation to test real-time feature serving latency. The PoC ends, the model is never productionized, but the Feature Store stays.
  • Ownership gaps after team changes: The ML engineer who built the Feature Store leaves the team. Nobody else knows it exists or what it's for.

“The recommendation system had been retired for five months. The Feature Store was still provisioned. Nobody had received a single alert.”

How CleanCloud Detects Idle Feature Stores

The gcp.vertex.featurestore.idle rule detects Vertex AI Feature Store online stores (both legacy and new-gen) with zero ReadFeatureValues requests over a 30-day window:

  1. Enumerates Feature Stores: Lists all Featurestore resources in each region of the project.
  2. Checks online store configuration: Only Featurestores with an online store configuration (Bigtable-backed) are evaluated — batch-only stores don't have the same billing profile.
  3. Queries ReadFeatureValues metrics: Looks up Cloud Monitoring for the aiplatform.googleapis.com/featurestore/online_serving/request_count metric over 30 days. Zero requests = idle finding.
  4. Estimates cost by node count: The finding includes an estimated monthly cost based on the Bigtable node count × $197/node/month.

The 30-day window (versus 7 or 14 days for other rules) reflects the reality that feature serving workloads can be genuinely bursty — a recommendation model that runs weekly batch jobs may only query the Feature Store once a week. The 30-day window distinguishes truly idle stores from ones with infrequent-but-real usage.

Why a 30-Day Idle Window?

CleanCloud uses different idle windows for different resource types. The logic:

  • SageMaker endpoints / Vertex AI endpoints (14 days): Real-time prediction endpoints that serve live user-facing traffic. If there's been no traffic for two weeks, it's almost certainly idle.
  • Bedrock / Azure OpenAI PTU (7 days): High-cost API reservations where even a week of zero invocations represents significant waste.
  • Feature Stores (30 days): Feature serving can be genuinely bursty. A store serving weekly batch scoring jobs may have quiet periods. 30 days is long enough to rule out seasonal quietness while still catching truly abandoned stores.

Adjusting the threshold: If your Feature Stores serve monthly batch jobs (e.g., monthly recommendation refreshes), increase the idle window to 45 or 60 days in cleancloud.yaml to avoid false positives.

Catching Idle Feature Stores in CI

.github/workflows/gcp-ai-waste.yml Weekly scan — includes Feature Store idle detection 
name: GCP AI/ML waste scan
on:
  schedule:
    - cron: '0 8 * * 1'

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.GCP_WORKLOAD_IDENTITY_PROVIDER }}
          service_account:            ${{ secrets.GCP_SERVICE_ACCOUNT }}

      - run: pip install 'cleancloud[gcp]'

      - run: |
          cleancloud scan --provider gcp \
            --all-projects \
            --category ai \

Frequently Asked Questions

Does Vertex AI Feature Store charge with zero ReadFeatureValues requests?

Yes. For Bigtable-backed online stores, billing is based on the number of Bigtable nodes allocated, not on query volume. An online store provisioned with three nodes bills ~$591/month regardless of whether it serves zero requests or millions.

What happens if I delete a Feature Store that's still in use?

Deletion removes the online store and all associated feature data. Any serving endpoint that queries it will fail. CleanCloud only flags stores with zero requests over 30 days — a store genuinely receiving traffic will not be flagged. Always verify the finding before acting on it.

Does CleanCloud detect both legacy and new-gen Feature Stores?

Yes. The gcp.vertex.featurestore.idle rule covers both the legacy Featurestore API (Bigtable-backed) and the new-gen Feature Store API. Both are checked for zero online serving traffic over the idle window.
