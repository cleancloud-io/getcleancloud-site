Azure OpenAI Provisioned Deployments:
$1,460/PTU/Month Whether You Use Them or Not

A platform team reserved 100 PTUs for a high-throughput Azure OpenAI deployment during a product launch. The launch wrapped up. The PTU reservation didn't. Three months later, $437,000 in unused compute capacity had quietly billed at full rate — with zero API requests.

What Is a Provisioned Throughput Unit?

Azure OpenAI offers two pricing models: pay-as-you-go (charged per token) and provisioned throughput (charged per reserved capacity unit). A Provisioned Throughput Unit — PTU — is a unit of dedicated model capacity that guarantees a consistent tokens-per-minute throughput for latency-sensitive workloads.

PTUs make sense for production applications that need predictable low-latency responses: a customer-facing chat interface, a real-time document processing pipeline, a voice assistant that can't tolerate cold-start delays. For those workloads, the cost premium is justified. For everything else — especially deployments left running after a project winds down — PTUs are an expensive mistake.

The billing mechanics are simple and unforgiving: PTUs bill at a fixed hourly rate regardless of how many API requests they receive. Zero requests. One request. A million requests. The bill is identical.

On-demand PTU pricing (approximate): ~$1,460 per PTU per month. A 100 PTU deployment costs ~$146,000/month at idle. Monthly commitment pricing reduces this, but any reservation for a workload that no longer exists is pure waste.

How PTU Waste Happens

PTU waste follows a predictable lifecycle that's nearly identical to idle SageMaker endpoints or AML compute clusters: a deployment is created for a specific use case, the use case ends, and nobody deletes the deployment.

The most common patterns we see:

  • Product launches: A team reserves PTUs to handle launch-day traffic spikes. The product goes live, traffic stabilizes, and the team migrates to pay-as-you-go — but forgets to delete the PTU deployment.
  • Proof-of-concepts: Engineering evaluates Azure OpenAI for a new feature. The PoC concludes (either shipped or abandoned). The PTU deployment stays.
  • Load test capacity: PTUs are provisioned to simulate production load during a stress test. The test finishes. The deployment doesn't.
  • Model version upgrades: A team provisions PTUs for a newer model version (GPT-4o replacing GPT-4). Traffic shifts to the new deployment. The old one isn't cleaned up.

Unlike compute resources, Azure OpenAI deployments don't show up prominently in cost dashboards alongside EC2 instances and storage. They're buried under the Azure OpenAI account resource, visible only if you know where to look. Cost alerts configured for the overall subscription may not break this out by deployment.

How CleanCloud Detects Idle PTU Deployments

The azure.openai.provisioned_deployment.idle rule targets Azure OpenAI deployments where the SKU indicates provisioned capacity — not pay-as-you-go token billing. Detection logic:

  1. Enumerate deployments: Lists all Azure OpenAI deployments across all accounts in the subscription using the Azure Cognitive Services management API.
  2. Filter to provisioned SKUs: Only deployments with a provisioned SKU (e.g. ProvisionedManaged, Provisioned) are evaluated — pay-as-you-go deployments don't accumulate idle cost the same way.
  3. Check API request traffic: Queries Azure Monitor for AzureOpenAIRequests metrics over the idle window (default 7 days). Zero requests = idle finding.
  4. Classify by PTU count: Higher PTU allocations produce higher-risk findings with proportionally higher estimated cost.

The Detection Gap Azure Native Tools Miss

Azure Cost Management shows that your subscription is spending money on Azure OpenAI. It does not tell you which specific deployment within that account is receiving zero traffic while billing at full PTU rate.

To detect idle PTU deployments natively you'd need to:

  • Navigate to each Azure OpenAI account in the portal
  • Open each deployment and check the monitoring tab
  • Manually correlate request count with the SKU type to identify provisioned deployments with zero traffic

In an organization with dozens of subscriptions and multiple Azure OpenAI accounts, this is not a scalable process. CleanCloud checks every provisioned deployment in every account across every subscription in a single scan — in under two minutes.

Catching PTU Waste in CI

Add an Azure AI/ML scan to your weekly CI/CD schedule. The azure.openai.provisioned_deployment.idle rule fires automatically when you pass --category ai:

.github/workflows/azure-ai-waste.yml Weekly scan — catches idle PTU within 7 days 
name: Azure AI/ML waste scan
on:
  schedule:
    - cron: '0 8 * * 1'   # Every Monday at 08:00 UTC

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: azure/login@v2
        with:
          client-id:       ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id:       ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - run: pip install 'cleancloud[azure]'

      - run: |
          cleancloud scan --provider azure \
            --category ai \
            --fail-on-confidence HIGH \
            --fail-on-cost 1460 \
            --output json --output-file azure-ai-findings.json

The --fail-on-cost 1460 flag means any single idle PTU deployment will fail the build. Adjust the threshold to match your organization's tolerance: a team comfortable ignoring small deployments might set it to 10000 (roughly 7 idle PTUs).

Suppressing Legitimate Low-Traffic Deployments

Not every low-traffic PTU deployment is waste. Some are kept warm for on-call scenarios, emergency AI assistants, or workloads with occasional-but-important usage patterns. CleanCloud's policy-as-code exception system handles these cleanly:

cleancloud.yaml — legitimate exception documented, expiring 
exceptions:
  - rule_id: azure.openai.provisioned_deployment.idle
    resource_id: openai-prod/incident-response-gpt4o
    reason: "On-call incident response assistant — low but critical usage, PTU needed for latency"
    expires_at: "2026-12-31"

Every exception is committed to git alongside your infrastructure. When the expiry date arrives, the exception must be renewed — forcing a periodic review of whether the deployment is still justified.

Required Azure Permissions

The rule requires Reader access on the subscription (covers Cognitive Services account enumeration) plus Azure Monitor read access:

The standard CleanCloud Azure setup (Reader role at subscription or Management Group level) covers all of these. No additional role assignments are required.

Frequently Asked Questions

Does Azure OpenAI charge for provisioned deployments with zero API requests?

Yes. PTU deployments reserve dedicated compute capacity and bill at a fixed hourly rate regardless of traffic. Zero API requests generates an identical bill to maximum throughput.

What's the difference between pay-as-you-go and provisioned throughput billing?

Pay-as-you-go charges per token processed — zero usage means zero cost. Provisioned throughput (PTU) reserves capacity and bills per hour regardless of usage. PTUs are appropriate for latency-sensitive production workloads; pay-as-you-go is better for variable or development workloads.

How does CleanCloud detect idle PTU deployments?

The azure.openai.provisioned_deployment.idle rule queries Azure Monitor for AzureOpenAIRequests over the configured idle window (default 7 days). Deployments with zero requests and a provisioned SKU are flagged HIGH confidence. Run: cleancloud scan --provider azure --category ai
