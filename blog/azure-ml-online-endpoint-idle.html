The Endpoint That Outlived Its Purpose

The product team wanted a live inference demo for a quarterly business review. An ML engineer deployed a real-time scoring endpoint on Azure ML — a Standard_NC6 GPU deployment behind a managed online endpoint, serving a fine-tuned classification model. The demo ran for 20 minutes. Everyone agreed it was impressive.

The follow-up task to delete the endpoint landed in a backlog. Nobody explicitly owned it. The sprint ended. The team moved to the next milestone. The endpoint stayed up.

Thirty-one days later, during a routine FinOps review, someone noticed a line item in Azure Cost Management that didn't map to any active project. The endpoint had been fully provisioned and healthy — provisioningState: Succeeded — the entire time. Zero scoring requests. Full GPU billing. No one had noticed.

Azure ML endpoints do not auto-suspend. A managed online endpoint in Succeeded state bills for its underlying compute continuously. There is no traffic-based idle detection built into the platform. Deletion is the only way to stop billing.

Why Endpoints Outlive Their Traffic

Azure ML managed online endpoints are production-grade infrastructure. They come with deployment slots, traffic routing, autoscaling configuration, and monitoring integration. That robustness is exactly what makes them easy to forget — they just keep working, even when no one is calling them.

The patterns that lead to idle endpoints are predictable:

  • Demo endpoints: Deployed for a business review, investor pitch, or internal showcase. Never scheduled for deletion because "it only takes a second."
  • Experiment endpoints: Deployed by an ML engineer to validate a model in a real serving environment. The experiment concluded; the endpoint didn't.
  • Deprecated model versions: Traffic was migrated to a new endpoint or deployment slot. The old endpoint was left as a fallback that was never removed.
  • Handover gaps: The engineer who deployed the endpoint left the team. The new owner didn't know it existed, or assumed someone else was responsible for cleanup.

The common thread: endpoints are deployed quickly and deliberately, then forgotten just as quickly once the immediate need passes.

How Azure ML Endpoint Billing Works

Azure ML managed online endpoints bill for compute resources at the deployment level. Each deployment specifies an instance type (SKU) and instance count. The billing clock starts the moment a deployment reaches the Succeeded provisioning state and runs continuously until the endpoint or deployment is deleted.

Unlike Azure Functions or Logic Apps, there is no consumption model. There is no concept of a "warm idle" vs. "cold idle" billing tier. The full VM rate applies whether the endpoint processes 10,000 requests per second or zero.

Key billing facts:

  • Billing is continuous: Endpoints bill 24/7 at the VM rate for the configured SKU and instance count.
  • Minimum instances matter: If you configured min_instances: 1 for zero-latency response, that instance bills even during complete traffic silence.
  • Scale-to-zero is not automatic: Autoscaling rules scale between your configured minimum and maximum. Setting min_instances: 0 allows scale-to-zero but requires explicit configuration.
  • GPU SKUs amplify cost: NC-series GPU deployments cost 3–6x more than equivalent CPU deployments. An idle NC6 deployment costs more per month than an idle CPU cluster that handles 10,000 requests/day.

How the Detection Rule Works

CleanCloud's azure.ml.online_endpoint.idle rule detects managed online endpoints that are fully provisioned but receiving no prediction traffic. It uses two complementary signals:

  1. Provisioning state check: The rule filters to endpoints with provisioningState == Succeeded. Endpoints in Creating, Updating, or Failed states are excluded — only healthy, billing endpoints are considered.
  2. Azure Monitor RequestCount metric: The rule queries the RequestCount metric for each endpoint over the configured idle window (default: 7 days). Endpoints with a confirmed zero-request count are flagged HIGH confidence.

Confidence levels reflect the quality of the traffic signal:

  • HIGH confidence: Azure Monitor confirms zero scoring requests across the full idle window AND the endpoint age meets or exceeds the threshold. This is a definitive no-traffic signal.
  • MEDIUM confidence: The metric query returned incomplete data (e.g., endpoint is newer than the window, or monitoring data is partially missing) but other signals suggest no active traffic.

Risk tiers are determined by the deployment's instance type:

  • CRITICAL risk: GPU-backed deployment (NC/ND/NV series) with an idle_ratio ≥ 2.0 — meaning the endpoint has been idle for at least twice the configured threshold. A 14-day-idle NC6 deployment on a 7-day window is CRITICAL.
  • HIGH risk: GPU-backed deployment within the normal idle window.
  • MEDIUM risk: CPU-only deployment regardless of idle duration.

Catching It in CI Before It Reaches 31 Days

The team in this scenario found the idle endpoint through a FinOps review 31 days after it was deployed. With CleanCloud integrated into CI, it would have appeared in a scan output within the first week.

.github/workflows/cleancloud-azure.ymlYAML
name: CleanCloud Azure ML Scan
on:
  schedule:
    - cron: '0 8 * * 1'  # Every Monday at 08:00 UTC
  workflow_dispatch:

jobs:
  cleancloud-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Azure login
        uses: azure/login@v2
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}

      - name: CleanCloud — Azure AI/ML scan
        uses: cleancloud-io/scan-action@v1
        with:
          provider: azure
          category: ai
          fail-on-confidence: HIGH

The fail-on-confidence: HIGH setting means the workflow fails — and the team gets a Slack/email notification — the first time a HIGH-confidence idle endpoint is detected. GPU endpoints with zero traffic for 7 days produce a HIGH confidence finding. The team would have known about this endpoint within a week.

Preventing Idle Endpoints Going Forward

Detection is the safety net. Prevention is the goal. A few practices that reduce endpoint sprawl:

  • Tag every endpoint with a TTL: Require a ttl or expires tag at deployment time. CleanCloud's untagged resource rules flag endpoints missing required tags, giving you a second layer of enforcement.
  • Delete demo endpoints after demos: Make endpoint deletion part of the demo runbook. If the endpoint needs to persist "just in case," set a calendar reminder for 72 hours later.
  • Use scale-to-zero for non-production endpoints: Set min_instances: 0 for experiment and staging endpoints. They'll incur cold-start latency but won't bill during idle periods.
  • Run CleanCloud weekly on your AI/ML resources: A weekly CI scan with fail-on-confidence: HIGH surfaces idle endpoints before they accumulate more than a week of idle spend.

Frequently Asked Questions

Does Azure ML charge for the endpoint itself, or just the deployments?

Billing is driven by deployments, not by the endpoint resource itself. An endpoint with no deployments incurs no compute cost. The moment a deployment is added and reaches Succeeded state, billing begins at the rate for the configured instance type and count.

Can I pause an Azure ML online endpoint to stop billing?

No. Unlike Azure VM compute instances, online endpoints do not have a stopped or paused state. To stop billing, you must delete the deployment or the endpoint. The Azure portal and CLI both provide az ml online-endpoint delete for this purpose.

What is the minimum idle window CleanCloud checks?

The default is 7 days. This is configurable via the idle_days parameter. For aggressive cost control on experiment environments, you can set idle_days: 3 to flag GPU endpoints that have been traffic-free for 3 days. For production environments where occasional traffic lulls are expected, you might use idle_days: 14.

Will CleanCloud catch endpoints that have low traffic but not zero?

No. The azure.ml.online_endpoint.idle rule specifically flags endpoints with zero scoring requests in the configured window. Low-traffic endpoints (e.g., 1 request/day) are not flagged. If you want to catch under-utilized endpoints, pair this with a cost-per-request analysis in Azure Cost Management.
