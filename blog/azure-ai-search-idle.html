The Search Index That Outlasted the Project

The team was building a document Q&A system using Azure OpenAI and Azure AI Search — a retrieval-augmented generation (RAG) architecture that had become the default approach for enterprise AI applications. They stood up an Azure AI Search service at Standard S2 tier, indexed 40,000 documents, and connected it to a chatbot frontend for a proof-of-concept.

The PoC worked well enough to demonstrate value, but the project was paused while waiting for security review and data governance sign-off. The ML engineer who built it moved on to another team sprint. The Azure AI Search service stayed provisioned, indexed, and billing.

Forty-seven days later, during a cost anomaly review, the Azure Cost Management dashboard flagged a consistent ~$523/month charge with no associated Azure DevOps pipeline, no active application using the endpoint, and no search traffic according to Azure Monitor. The team had been paying for an idle search index for a month and a half.

Azure AI Search does not scale to zero. Standard-tier and higher services bill continuously by the hour for every provisioned replica-partition unit, regardless of query volume. Only the Free tier is exempt from idle billing. Deletion is the only way to stop charges on a paid tier.

Why AI Search Services Outlive Their Projects

Azure AI Search services are more persistent than typical compute resources because they carry data — the indexed documents represent real work that teams don't want to throw away "just in case." That instinct to preserve indexed data is what keeps idle services running.

The common patterns:

  • RAG/AI application prototypes: Built during a hackathon or sprint to demonstrate AI-powered search. The prototype is shelved; the search backend stays up.
  • Seasonal or batch workloads: A search service built for a product launch or event. Traffic peaked during the launch window, then dropped to zero.
  • Migrated applications: Search traffic was moved to a newer service or a different search backend. The old service was left as a fallback that was never decommissioned.
  • Development and staging environments: Search services provisioned at production-tier scale for performance testing, then forgotten after the test concluded.

How Azure AI Search Billing Works

Azure AI Search uses a replica-partition unit (SU) billing model. The service bills for the number of replicas multiplied by the number of partitions, each charged at the hourly rate for the selected tier. A service with 2 replicas and 2 partitions has 4 SUs and bills at 4× the base tier rate.

Key billing facts:

  • Billing starts at provisioning: The moment a paid-tier service is created, the billing clock starts at the configured replica/partition count.
  • Query volume has no effect: Unlike API-based services, search query volume does not affect your bill. Zero queries/day costs the same as 1 million queries/day at the same SU count.
  • Indexing operations are separate: Document indexing (AI enrichment pipelines, custom skills) can incur additional charges, but base SU billing is always on.
  • Semantic ranker has incremental cost: Semantic search queries add per-query costs, but zero semantic queries still incur the base SU charge.
  • Only the Free tier scales to zero: F1 (Free) tier is the only tier that can be idle without cost. It supports only one service per subscription and has capacity limits that make it unsuitable for production workloads.

How the Detection Rule Works

CleanCloud's azure.ai_search.idle rule detects Standard-tier and higher Azure AI Search services that are provisioned but receiving no search traffic. It operates over a 30-day monitoring window to distinguish genuinely abandoned services from those with infrequent but legitimate traffic.

Detection logic:

  1. Tier filter: The rule only evaluates Standard, Standard2, Standard3, StorageOptimizedL1, and StorageOptimizedL2 tiers. Free and Basic tiers are excluded. Standard and above are the tiers where idle cost is meaningful.
  2. Azure Monitor metric query: The rule queries the SearchQueriesPerSecond metric aggregated over the full 30-day window. A confirmed zero-query result triggers HIGH confidence.
  3. Cost-based risk classification: Risk tier is determined by the estimated monthly cost of the idle service. Services costing ≥ $1,000/month are flagged HIGH risk. Services below that threshold are MEDIUM risk.

Confidence levels:

  • HIGH confidence: Azure Monitor confirms zero SearchQueriesPerSecond across the full 30-day window.
  • MEDIUM confidence: Metric data is incomplete (e.g., the service is newer than 30 days, or monitoring gaps exist), but available data suggests no active traffic.

Catching It in CI Before 47 Days Pass

The 30-day monitoring window means that the earliest an idle service can be flagged HIGH confidence is after 30 days of zero queries. For teams running weekly scans, an idle service provisioned today would appear as MEDIUM confidence during the first 30 days (incomplete data window) and escalate to HIGH once 30 days of zero-query data is confirmed.

.github/workflows/cleancloud-azure.ymlYAML
name: CleanCloud Azure AI Scan
on:
  schedule:
    - cron: '0 8 * * 1'  # Every Monday at 08:00 UTC
  workflow_dispatch:

jobs:
  cleancloud-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Azure login
        uses: azure/login@v2
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}

      - name: CleanCloud — Azure AI scan
        uses: cleancloud-io/scan-action@v1
        with:
          provider: azure
          category: ai
          fail-on-confidence: HIGH

Running with fail-on-confidence: HIGH ensures that a HIGH-confidence idle search service — confirmed zero queries for 30 days — fails the CI check, notifying the team before a second billing month passes.

Reducing AI Search Sprawl

The 47-day idle service in this story was the result of a governance gap: no policy requiring AI search services to have an owner tag or a TTL, and no automated visibility into which services were receiving queries. Fixing the gap requires both prevention and detection.

  • Require owner and project tags: Azure Policy can enforce that all Standard-tier and above search services carry an owner and project tag at creation time. CleanCloud's untagged resource rules provide a secondary check.
  • Use naming conventions that signal environment: A service named rag-prototype-search-dev signals to any reviewer that it may be non-production and subject to cleanup.
  • Establish a prototype lifecycle policy: Any search service provisioned for a PoC should have a maximum lifetime (e.g., 30 days) without a formal request to extend. Encode this in your team's runbook.
  • Run CleanCloud weekly on AI resources: The 30-day detection window means MEDIUM confidence findings appear in the first month. Reviewing them promptly prevents escalation to HIGH.
  • Export index definitions before deletion: If the concern is losing indexed content, export the index schema and re-index later if the project is revived. Re-indexing is cheaper than keeping the service running indefinitely.

Frequently Asked Questions

Does Azure AI Search have an auto-pause or idle mode?

No. Azure AI Search Standard-tier and above services do not have a pause, suspend, or idle mode. The service bills continuously at the provisioned SU count. The only way to stop billing is to delete the service or downgrade to the Free tier (which has significant capacity limits).

Why does CleanCloud use a 30-day window instead of 7 days?

Azure AI Search is commonly used for infrequent but legitimate workloads — batch document retrieval, monthly report generation, seasonal search traffic. A 7-day window would generate false positives for these patterns. The 30-day window is long enough to distinguish genuinely abandoned services from infrequently used ones. It is configurable via the idle_days parameter if your workload requires a different threshold.

What if my search service has queries from indexer pipelines but no user traffic?

Azure Monitor's SearchQueriesPerSecond metric counts user-facing search API calls, not indexer operations. Indexer runs are tracked separately as DocumentsProcessedCount. If your service is running indexers but receiving zero user queries, the rule will still flag it — which may be intentional if you are pre-indexing for a future go-live.

Is Basic tier covered by this rule?

No. The azure.ai_search.idle rule targets Standard tier and above. Basic tier services bill at a lower rate (~$75/month) and are common for small-scale production workloads. CleanCloud focuses the AI Search rule on Standard+ tiers where idle spend is materially significant.
