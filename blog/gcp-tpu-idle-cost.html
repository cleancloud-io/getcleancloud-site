Cloud TPU Idle Costs:
$12 an Hour for a Node That Isn't Training Anything

A research team finished a large-scale pretraining run on a TPU v4 pod. They intended to delete it after reviewing the checkpoints. The code review took two weeks. The TPU stayed in READY state the entire time — billing $12.88/hour, 24 hours a day, for a node with zero workload.

How Cloud TPU Billing Works

Cloud TPUs are Google's custom AI accelerators designed for large-scale machine learning workloads — training large language models, image models, and recommendation systems that would take impractical amounts of time on GPUs alone.

Unlike Compute Engine VMs (which can be stopped to avoid billing), Cloud TPU nodes bill continuously in READY state regardless of whether any workload is running on them. READY is the state a TPU node enters after creation and after a job completes — it's the standby state, and it's not free.

The reason: TPU capacity is physically reserved when a node is created. Google is holding that silicon for you. Billing reflects that reservation, not the utilization of it.

No "stopped" state for TPUs: Unlike VMs, you cannot stop a TPU node to avoid billing. The only cost-free state is deletion. Recreating a TPU node typically takes 2–5 minutes.

How TPU Waste Happens

The most common patterns causing idle TPU spend:

  • Training job completed, node not deleted: A pretraining or fine-tuning run finishes. The engineer reviews checkpoints, considers next steps, and forgets the TPU is still allocated. Days pass.
  • Experimental nodes kept "just in case": A team uses a TPU node for hyperparameter sweeps. The experiments conclude, but the node is kept available to avoid the 2–5 minute recreation time if they want to run another experiment soon. "Soon" doesn't come.
  • CI/CD pipeline creates TPU, cleanup step fails: An automated training pipeline provisions a TPU node, runs a job, but the cleanup step fails silently — perhaps due to a permissions error or a pipeline timeout. The node stays allocated indefinitely.
  • Abandoned proof-of-concept: A team evaluates JAX on TPUs for a new model architecture. The evaluation concludes (or is deprioritized). The TPU node from the PoC is never deleted.

“Two weeks of idle billing. $4,381 in waste. The team thought someone else had cleaned it up.”

How CleanCloud Detects Idle TPU Nodes

The gcp.tpu.idle rule detects Cloud TPU nodes (v2 through v6e) in READY state with near-zero utilization over the idle window (default 7 days):

  1. Lists all TPU nodes: Enumerates TPU nodes across all zones in the project using the Cloud TPU API.
  2. Filters to READY state: Only nodes currently in READY state are evaluated — nodes in CREATING or running a job are excluded.
  3. Checks duty cycle: Queries Cloud Monitoring for the tpu/duty_cycle metric over the idle window. Nodes with duty_cycle ≤ 2% for the full window are flagged as idle.
  4. Classifies by generation: v4 and v5p nodes are flagged CRITICAL risk due to their higher per-hour cost. v2/v3 nodes are HIGH.

The Duty Cycle Signal

Cloud TPU exposes a duty_cycle metric via Cloud Monitoring that measures the fraction of time the TPU cores are actively processing. A node running a training job will show duty cycles of 70–99%. A node sitting idle in READY state with no workload will show duty cycles at or near 0%.

CleanCloud uses a 2% threshold (not 0%) to account for background system processes and metric sampling noise. A node consistently below 2% for a week is definitively not running any meaningful workload.

Why not detect idle TPUs without metrics? READY state alone isn't sufficient — a node between job steps may be in READY state briefly. The duty cycle metric over 7 days confirms the node has had no meaningful activity over an extended period, preventing false positives on nodes actively used with infrequent batch schedules.

Frequently Asked Questions

Does GCP charge for Cloud TPU nodes in READY state?

Yes. Cloud TPU nodes bill from the time they enter READY state until they are deleted. There is no "stopped" state that avoids billing. READY with zero workload is full idle billing at the on-demand rate for that TPU version and chip count.

Can I pause a Cloud TPU node to avoid billing?

No. Unlike Compute Engine VMs, TPU nodes don't support a stopped/paused state. Deletion is the only way to stop billing. Recreating a TPU node from scratch typically takes 2–5 minutes, which is a reasonable tradeoff given the hourly cost of keeping one allocated indefinitely.

What TPU versions does CleanCloud detect?

The gcp.tpu.idle rule detects v2, v3, v4, v5e, v5p, and v6e TPU nodes. All generations that support Cloud Monitoring duty_cycle metrics are covered.
