The Sprint That Ended Without a Cleanup

A computer vision team at a retail company was building a product recommendation model. Their ML platform engineer provisioned a Standard_NC24s_v3 Azure ML Compute Instance for the lead data scientist — a single-VM interactive development environment with four NVIDIA V100 GPUs and 112 GB of GPU memory. The setup was deliberate: the model required multi-GPU experimentation and the data scientist needed a Jupyter environment that could run training loops interactively.

The sprint went well. The model reached production accuracy targets by week three. The data science lead moved to the next project. The compute instance stayed Running.

Three weeks later, a platform audit flagged a suspiciously high Azure ML billing line item. The platform engineer ran CleanCloud:

Why Azure ML Compute Instances Stay Running

Azure ML Compute Instances are fundamentally different from Azure ML Compute Clusters. A Compute Cluster scales to zero between jobs — if min_nodes: 0 is set, it costs nothing when idle. A Compute Instance is a persistent, always-on VM. It does not scale. It does not stop automatically. It has one state that costs nothing: Stopped.

While Running, it bills at the full VM rate — whether you are actively running a notebook kernel, connected via VS Code, or have not touched it in a month. The Azure ML portal shows the instance as Running either way. There is no visual distinction between “Running and actively used” and “Running and forgotten.”

The key difference from a Compute Cluster: stopping a Compute Instance costs nothing. The VM is deallocated. The persistent disk that holds your notebooks and conda environments is retained. When you restart the instance, your work is exactly where you left it — only the startup time increases by a minute or two.

The pattern: Data scientists close the browser when they finish work but rarely explicitly stop the instance. The Azure ML portal's “Run” button for notebooks does not stop the instance — it stops the kernel. The instance stays Running until someone clicks the Stop button in the Compute pane.

How the Detection Rule Works

The azure.ml.compute_instance.idle rule checks each Running Compute Instance for recent control-plane activity using the last_operation.operation_time field. This timestamp is updated by the Azure ML control plane whenever a Start, Stop, Restart, or Create operation occurs on the instance.

An instance that has had no operation for 14+ days is a strong candidate for idle waste. The signal mirrors the approach used by aws.sagemaker.notebook.idle — both rules use the last control-plane timestamp as a proxy for activity, since neither platform publishes per-instance utilisation metrics by default.

Confidence levels:

  • HIGH: last_operation.operation_time (or last_modified_at fallback) is ≥ 14 days ago AND instance age ≥ 14 days
  • MEDIUM: Signal is at 75% or more of the threshold on both measures, or age-only fallback applies (when neither timestamp is available — age alone is not evidence of idleness)

Risk levels:

  • CRITICAL: GPU instance (NC/ND/NV series) AND idle_ratio ≥ 2.0 (idle for 28+ days at the default 14-day threshold)
  • HIGH: GPU instance (NC/ND/NV series)
  • MEDIUM: CPU-backed instance
Detection logic (simplified) azure.ml.compute_instance.idle 
for instance in ml_client.compute.list(workspace):
    if instance.state != "Running":
        continue
    last_op = instance.last_operation.operation_time  # or last_modified_at
    idle_days = (now - last_op).days
    if idle_days >= 14 and instance_age_days >= 14:
        confidence = "HIGH"
        idle_ratio = idle_days / 14
        if is_gpu and idle_ratio >= 2.0:
            risk = "CRITICAL"
        elif is_gpu:
            risk = "HIGH"
        else:
            risk = "MEDIUM"

Why This Keeps Happening

Azure ML Compute Instances are created as personal development environments — one per data scientist, typically provisioned by a platform team and shared across projects. The lifecycle problem is structural:

  • Sprint handovers: The data scientist who created the instance moves to a new project. Nobody else uses the instance. It stays Running because stopping it feels like deleting someone else’s work.
  • Holiday periods: Instances left Running over holidays accumulate days of idle cost with no way to detect it short of a dedicated scan.
  • Project completion: The model ships to production. The pipeline is containerised and running on AKS. The development instance that built it sits idle.
  • No auto-stop by default: Unlike some managed notebook services, Azure ML Compute Instances have no built-in idle timeout that automatically stops the VM when not in use. Auto-stop must be explicitly configured.

Auto-stop is available but not on by default. Azure ML supports an idle shutdown policy for Compute Instances. It can be configured per-instance via the portal, CLI (az ml compute update --idle-time-before-shutdown-minutes 60), or at workspace level. Teams that set this policy report significantly lower idle cost. CleanCloud still flags instances approaching or exceeding the threshold as a backup signal.

Catching It in CI: Weekly Scan

The setup that catches idle Compute Instances before they accumulate significant waste is a weekly scan against all Azure subscriptions, with fail-on-confidence: HIGH to catch GPU instances:

.github/workflows/azure-ai-waste.yml Azure ML Compute Instance — weekly scan 
name: Azure AI/ML waste scan
on:
  schedule:
    - cron: '0 8 * * 1'   # Every Monday at 08:00 UTC

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - uses: cleancloud-io/scan-action@v1
        with:
          provider: azure
          category: ai
          fail-on-confidence: HIGH
          fail-on-cost: '500'
          output: json
          output-file: azure-ai-findings.json
          artifact-name: azure-ai-report

With this setup, a Compute Instance that goes idle will be caught on the first Monday after its 14-day threshold is crossed. For a Standard_NC24s_v3, that means catching ~$4,400 of waste instead of months of accumulation.

Required Azure Permissions

The rule needs read-only access to Azure ML workspaces and their compute resources. Add these to your CleanCloud service principal role:

  • Microsoft.MachineLearningServices/workspaces/read
  • Microsoft.MachineLearningServices/workspaces/computes/read

The rule is read-only — it never stops, modifies, or deletes instances. All findings are candidates for human review. Use the security/azure/ai-readonly-role.json in the CleanCloud repository for the minimal role definition.

Frequently Asked Questions

Does Azure ML Compute Instance charge when no notebooks are open?

Yes. The instance bills at the full VM rate whenever it is in Running state — regardless of whether any Jupyter kernels, VS Code Server sessions, or RStudio connections are active. Stopping the instance is the only way to stop billing. The disk that stores your notebooks is retained and resumable.

How do I stop an Azure ML Compute Instance when idle?

Via the Azure ML portal: go to Compute › Compute Instances, select the instance, and click Stop. Via CLI: az ml compute stop --name instance-name --workspace-name ws --resource-group rg. Via Python SDK: ml_client.compute.begin_stop(instance_name).wait(). To prevent future occurrences, configure the idle shutdown policy on the instance.

What's the difference between a Compute Instance and a Compute Cluster?

A Compute Cluster is designed for batch training jobs and scales between zero and N nodes. With min_nodes: 0, it costs nothing when idle. A Compute Instance is a persistent single-VM interactive development environment — it does not scale automatically and must be explicitly stopped to stop billing.
